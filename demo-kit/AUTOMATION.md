# Automation map — what a coding agent can run vs. what is portal-only

**Purpose.** If you hand this kit to a coding agent (GitHub Copilot agent, Copilot CLI, etc.) with an authenticated `az login` session, the table below tells it — and you — exactly which steps it can execute and which steps a human must click through in the Foundry (new) portal.

**Governing statement (Control Plane overview):** "You can currently access these features through the Foundry portal only." — https://learn.microsoft.com/en-us/azure/foundry/control-plane/overview
This applies to the **Operate** panes (Overview, Assets, Compliance) and the **Manage > AI Gateway** pane. Everything that lives *underneath* those panes (Azure API Management, Azure Policy, Application Insights, the Foundry agents data-plane API) has its own official API or IaC, and that is what the "Automatable equivalent" column points to.

## What this means for a hand-off to a coding agent

**Agent-runnable (unattended, given `az login` + roles in `00-prereqs/roles.md`):**
`00-prereqs/check_prereqs.sh` → `01-infra/deploy_foundry_standard.sh` (Foundry + project + App Insights + eval RBAC) → *(optional)* `project-ai-gateway.bicep` to enable further projects on an existing gateway → `02-agents/*` (versions, selector, hosted agent via azd) → `03-custom-agent/external_agent_register.py` → `04-traffic/send_traffic.py` → `05-evaluation/continuous_eval_rule.py`, `scheduled_eval_and_redteam.py`, `agent_insights.py` → `06-cost/apim-policies/*.xml` applied to APIM → `07-guardrails/rai_policy_put.sh` → `08-cicd/*` (once in a repo) → `09-identity-killswitch/*.sh`.

**Human-in-the-portal (one-time set-up, ~20 min, then live in the demo):**
1. **Manage > AI Gateway > Add AI Gateway** on the Foundry resource (account level) — do this first; the Bicep for projects depends on it.
2. **Operate > Overview > Register asset** for the LangGraph custom agent — only after App Insights is connected ("If you configured Application Insights after you registered the custom agent, you need to unregister the agent and register it again").
3. **Manage > AI Gateway > Token management > + Set limit** — *or* skip it and rely on the APIM policy from step C (choose one).
4. **Operate > Compliance > Create policy** — at least 30 minutes before the session ("Allow up to 30 minutes for the guardrail policy to appear").
5. **Operate > Assets > Update status > Block / Unblock** — live, during the demo.
6. **Build > agent > Monitor > gear > Alerts (preview)** — turn on before the session so alerts have traffic to evaluate.

**Suggested prompt for the coding agent:**
> "Read `demo-kit/README.md` and `demo-kit/AUTOMATION.md`. Run the agent-runnable steps in order against subscription `<id>` in region `<region>`, using the `.env` I provide. Stop before account-level Add AI Gateway, the optional Foundry Register asset wizard, Token management pane, Create guardrail policy, custom-agent Block/Unblock, and Alerts. Deploy the external LangGraph runtime and stable APIM gateway from the provided Bicep and source."

## Corrections to earlier statements in this engagement
- "Add AI Gateway — no documented API" was **too strong**: account-level enablement is portal-only on the official record, but **project-level enablement and the AI Gateway tier have official Bicep** (foundry-samples `01-connections/project-ai-gateway`, `01-connections/ai-gateway-tier`).
- "Token limits — portal-only" was **incomplete**: the Foundry pane is portal-only, but the identical 429/403 enforcement is an official APIM policy (`llm-token-limit`) that can be deployed as code.
- "Guardrail policy — portal-only" **stands**, with the nuance that the *guardrail configuration* it enforces is scriptable (RAI policy ARM/azd/SDK) and other Foundry governance rules ship as official Azure Policy definitions.
- "Register asset", "Block/Unblock (custom)" and "Alerts (preview)" — **confirmed portal-only** on the official record as of 24 Sept 2026.
